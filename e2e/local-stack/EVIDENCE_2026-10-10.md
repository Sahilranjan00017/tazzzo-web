(`lib/redact-patterns.mjs`): one-time OTP `challengeId` / `grantId` values are replaced by `<redacted>`, and every mobile number is masked as `+91XXXXXX1234`. Line numbers and all verdicts are unchanged.
Three screenshots that showed a delivery phone number (`j26-review`, `j26-confirmation`, `j28-order-delivered`) were deleted from both runs rather than edited; `screens/` references to them in the transcript lines are historical.
New runs mask phone numbers in screenshots (`tests/web.ts`) and `journeys.sh` runs `lib/redact-evidence.mjs --check` after every run (it fails the step if any number or one-time id remains).

## Product bugs found

Severity is my judgement for a launch decision. None was fixed here (task rule); each reproduces in both runs.

### B1 (LOW) backend: a quoted CSV id with a trailing newline is accepted as a valid id in async import jobs

- Repro: create an import job, upload `text/csv` with a row whose id cell is `"TZP-1<LF>"` (quoted, newline before the closing quote), validate. The row is `VALID` with id `TZP-1`; `docs/ops/BULK_IMPORT.md` says an id of `TZP-1` followed by a newline is `INVALID` / `INVALID_ROW`.
- Root cause: `services/catalog-service/src/main/java/com/tazzzo/bulkimport/jobs/ImportCsvParser.java:94` and `:123` call `.trim()` on every cell before the id grammar check (the class comment, line 27, documents the trimming; the runbook paragraph on the grammar contradicts it). The JSON path rejects the same id correctly (J04.13, passes).
- Impact: low. The stored id is canonical (`TZP-1`), no injection. It is a silent normalisation, and the two documents disagree.
- Evidence: J04 check J04.12, `run1/transcript.txt` L183 and the job-row listing above it; `run2` L183.

### B2 (LOW) backend: malformed-query 400s use a different error envelope from every other consumer 400

- Repro: `GET /v1/search?q=%ZZ` answers `{"code":"INVALID_REQUEST","message":"invalid request","request_id":"req_..."}` (snake_case id, no `retryable`); `GET /v1/categories/TZV-000001/products?page_size=abc` answers `{"code":"INVALID_REQUEST","message":"invalid request","requestId":"...","retryable":false}`. Three distinct 400 shapes exist across the malformed-query probes.
- Root cause: `catalog/api/MalformedQueryFilter.java:95` builds `ConsumerDtos.ConsumerError(code, message, requestId)` (filter-level, before routing), while the commerce routes use `commerce/api/dto/ErrorEnvelopeDto` (`requestId`, `retryable`). No input is echoed and the status/code/message are fixed, so the "fixed 400" property holds; the field names do not.
- Impact: low. A client that parses `requestId`/`retryable` (the storefront and app do for commerce errors) gets nothing from this one.
- Evidence: C6 check C6.12, `run1/transcript.txt` L1764-1765 (the three shapes are listed); `run2` L1764-1765.

### B3 (LOW) backend: OTP request reports its windows one second short, and -1 when the resend cooldown is 0

- Repro: `POST /v1/auth/otp/request` with the default TTL 300 returns `expiresInSeconds: 299`; with `TAZZZO_OTP_RESEND_COOLDOWN_SECONDS=2` it returns `resendAfterSeconds: 1`. With the cooldown set to `0` (a value the config accepts, `>= 0`) it returns `resendAfterSeconds: -1`, and the storefront's response check (`apps/storefront/src/server/backend/customer.ts`, `resendAfterSeconds` `min(0)`) rejects it as malformed, so sign-in is unavailable (seen during bring-up: `storefront_backend_malformed path=/v1/auth/otp/request` in the storefront log; the run files use cooldown 2).
- Root cause: `services/catalog-service/src/main/java/com/tazzzo/auth/otp/OtpService.java:155-156`: `Duration.between(sentAt, <date read back from Mongo>).getSeconds()`. Mongo truncates to milliseconds, so the difference is a hair below the configured value and `getSeconds()` floors it (negative durations floor to -1).
- Impact: low (the production cooldown is 30 s, which never reaches -1; the UI countdown is one second short).
- Evidence: C4 check C4.2, `run1/transcript.txt` L1700; `run2` L1700. The `-1` case is from bring-up, not part of the committed run (it needs a different backend setting).

### Observations (not counted as bugs)

- **O1 media metadata:** the backend verifies only _newly referenced_ media keys (`docs/ops/MEDIA_STORAGE.md`). Re-declaring an already referenced key with a different `width` (801 vs the stored header's 800) is accepted (200), so declared dimensions of an existing asset can drift from the file. New keys are fully checked (J14: bad dimension, bad type, bomb header, truncated header, text-as-PNG, never-uploaded, foreign key, forged key all 422). `run1/transcript.txt` L755.
- **O2 import PAUSED path not reachable by a datastore outage:** a 40 s outage (J08, `docker stop` of Mongo) was ridden out by the worker/driver (job COMPLETED, nothing lost or duplicated); `PAUSED` + `POST /resume` could not be forced this way, so that exact path is **not verified**. What was verified: SIGKILL of the backend mid-apply, restart, lease takeover after ~75 s (lease 60 s here, 300 s default), COMPLETED with exactly 400 products, and `POST /resume` on a non-PAUSED job is refused with 409. `run1` L436, L468.
- **O3 cart:** the `PRICE_CHANGED` line note is raised only for an aging cart (`CartEnricher`); a fresh cart silently shows the current price. The "Proceed to checkout" link is shown while a line is blocked; `/checkout` then withholds Place order (J25 asserts both).
- **O4 OTP LOGGING mode** cannot be used to sign in by design (it never logs the code). The harness uses the real HTTP adapter against a loopback receiver. The task text asked for the LOGGING provider; that is not possible.
- **O5 staff roles** are human-only: the `order-ops`/`support-agent` journeys use an ID token verified against a loopback JWKS (documented `jwks-uri` override), not the static tokens (which get 403 on `/api/v1/admin/orders`, asserted in J28).
