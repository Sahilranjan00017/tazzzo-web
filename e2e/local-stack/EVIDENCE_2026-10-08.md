# E2E-MEDIA local verification: evidence, 2026-10-08

**Bottom line:** every requested TEST passed in one run on a freshly built stack (11/11 Playwright tests, 5.1 min). Two
things were **not** verified:

- **App on a device:** the app was checked on the JVM only, so no emulator or simulator rendering was observed.
- **CMS UI screens:** the CMS steps were sent through the API, because the CMS cannot sign in against the real backend locally.

All of it ran on one Mac. Nothing touched AWS or a shared environment.

2. `up.sh` started the containers, initiated `rs0`, created the bucket, set CORS, started the CDN stand-in, and brought up the backend. Readiness check: `{"status":"UP",…}`.

5. `journeys.sh` ran the 11 tests.

Feature worktrees afterwards: backend, store, CMS and app all at their PR heads with **0 changes**. The app test file is
copied in for each run and removed on exit.

## Product findings (recorded, not fixed)

1. **The app drops product ids that the backend, CMS and website accept.** Contract divergence, not exercised at runtime here.
   - The app requires `^TZP-[0-9]+$` for rail ids (`tazzzo-app` `composeApp/src/commonMain/kotlin/com/tazzzo/app/data/content/ContentModels.kt:111`, the `PRODUCT_RAIL` mapping in `toDomain()`; banner links use the same rule, `ContentLink.PRODUCT_ID` at `ContentModels.kt:37`).
   - Everything else accepts `TZP-[A-Za-z0-9-]{1,40}`: the backend (`ContentBlock.java:152,154`), the CMS (`apps/admin/src/lib/home-content.ts:62,66`) and the storefront (`apps/storefront/src/lib/ids.ts:8`).
   - The backend's own product API accepts such ids; `MediaUploadEndToEndIT` creates `TZP-MED-3`.
   - Repro: publish a `PRODUCT_RAIL` with `ids:["TZP-MED-3"]`. The website renders it; the app silently drops the rail, and a `product:TZP-MED-3` banner link is not tappable.
   - The storefront already notes the OpenAPI/served mismatch (`ids.ts:5-6`).
   - Needs a ruling on which grammar is canonical.
2. **The banner image placeholder is not centred.** Cosmetic, storefront.
   - Cause: `.banner__media { display:block }` (`apps/storefront/src/app/globals.css:199-201`) comes after `.img-fallback { display:flex; align-items:center; justify-content:center }` (`globals.css:170-177`) with equal specificity. On a banner placeholder, which carries both classes, the mark therefore sits top-left.
   - Visible in `screens/t14-website-home-cdn-down.png`; compare the centred card and PDP placeholders.
3. **The app cannot be pointed at a local backend in debug.** Testability gap, not a defect:
   - the base URL comes from a fixed https enum, and `debugOverride` is never set;
   - `usesCleartextTraffic="false"` is set, with no debug network-security config;
   - images must be https.

   This is why on-device verification was not possible without app changes.

## Harness issues met (fixed in the harness, not product)

- **CMS-origin page:** a page fulfilled by Playwright's `page.route` has no address, so Chromium's Local Network Access check refused its PUT to the loopback store. The console said: "Permission was denied for this request to access the `loopback` address space". The harness now serves the CMS-origin page from a real loopback server; no browser flag is used.
- **Storefront cache:** its 60 s cache made a cold PDP check race the media write, so the PDP and home checks now reload until the expected state appears, and log the latency.
- **Echoed key id:** versitygw echoes `AWSAccessKeyId` in signature errors, so the transcript redacts it.
- **Stale log line:** `up.sh` printed the previous run's `media_storage` line because the log is appended; it now prints the latest match.
- **Temp download path:** the CDN download in TEST 4 was resolved relative to the evidence directory, so the run broke when `E2E_EVIDENCE_DIR` was overridden. It is now anchored to the harness directory.
- **Backend bind address:** the jar listened on `*:8080`, Spring's default. It now runs with `--server.address=127.0.0.1`, so every listener is loopback-only (see the `### listeners` line in `stack-cycle.txt`).
- **Final evidence:** all of the evidence in this file comes from one fresh cycle (`down` → `up` → `seed` → `web` → `journeys`) run on the committed code after these fixes.

## Not verified

- On-device app rendering (Android emulator or iOS simulator).
- CMS UI screens.
- Desktop-only banner art (`desktopImageAssetKey`).
- AWS S3 / CloudFront behaviour beyond what versitygw and the stand-in emulate. In particular: real CloudFront caching and invalidation, OAC policy, and the `ListBucket`-dependent 404-vs-403 behaviour.
